# Постоянная система игроков

Зафиксировано 25 сентября 2026 года. Документ описывает работающий код, а не план будущей разработки. Исходное состояние на эту дату: восемь игроков с фотографиями. Переписывать их записи или изображения ради очередного матча не требуется.

## Главный принцип

Один человек → один постоянный `id` → одна запись в общей базе → повторное использование во всех составах. База накапливается от матча к матчу и не очищается при обновлении `/match-center/`. Она общая для клубных матчей, сборных и будущих составов Кубка мира 2027. Клуб и турнир не входят в идентификатор: переход игрока в другую команду не создаёт нового человека.

Автоматическим является распознавание уже внесённых игроков при открытии страницы. Автоматического поиска фотографий в интернете и фонового пополнения базы сейчас нет: новые проверенные записи добавляются при обслуживании проекта.

## Файлы и ответственность

| Путь от корня | Назначение |
| --- | --- |
| `assets/players/players.json` | Единственная рабочая база игроков; её читает сайт |
| `assets/players/*.webp` | Локальные оптимизированные фотографии |
| `assets/players/README.md` | Авторство, лицензии и история подготовки опубликованных снимков |
| `assets/js/player-cards.js` | Загрузка базы, сопоставление имён, события, размещение и закрытие карточки |
| `assets/css/player-cards.css` | Оформление имён-кнопок, карточки и сенсорных элементов |
| `menu.js` | При наличии `.lineups` подключает CSS и модуль карточек |
| `match-center/index.html` | Нынешняя оперативная страница матча со статическими составами |
| `checks/player-cards.html` | Неиндексируемая проверка живой страницы в узкой/широкой области просмотра |
| `scripts/check_players.py` | Проверка базы, уникальности, файлов и обязательных сведений; входит в `npm test` |
| `scripts/player_photo_sources.json` | Журнал проверенных источников и результатов загрузки; не вторая база игроков, сайтом не читается |

Старый адрес `match-center/toulouse-bordeaux/index.html` сейчас перенаправляет посетителя на общий Матч-центр. Не восстанавливать по этому документу старые составы или отдельную базу.

## Формат записи

Оболочка файла: `{"version": 1, "players": [...]}`. Пример фактической записи (порядок свойств значения не имеет):

```json
{
  "id": "will-stuart",
  "name": "Уилл Стюарт",
  "aliases": ["Уилл Стюарт", "Will Stuart"],
  "image": {
    "src": "/assets/players/will-stuart.webp",
    "width": 353,
    "height": 440,
    "year": 2021,
    "author": "Stefano Delfrate",
    "source": "https://commons.wikimedia.org/wiki/File:Will_Stuart_2021.jpg",
    "license": "CC BY-SA 2.0",
    "licenseUrl": "https://creativecommons.org/licenses/by-sa/2.0/",
    "changes": "Подготовка исходного файла: Stemoc. Уменьшение и перевод в WebP; производная распространяется по CC BY-SA 2.0."
  }
}
```

- `id`: постоянный уникальный идентификатор латиницей в нижнем регистре, слова через дефис. Не менять при исправлении написания имени. Для тёзок выбрать разные устойчивые идентификаторы после проверки личности.
- `name`: полное русское имя для заголовка карточки и `alt` фотографии.
- `aliases`: точные полные варианты написания на русском и/или других языках. Новую транслитерацию добавлять сюда, не создавать дубликат игрока. Не добавлять общую фамилию вместо полного имени.
- `image.src`: путь от корня сайта к существующему локальному WebP, не URL внешнего фотохостинга.
- `width`, `height`: реальные размеры подготовленного файла, не исходника.
- `year`: год съёмки, а не загрузки в репозиторий; снимок не обязан показывать текущую клубную форму.
- Авторство, страница источника, название/версия лицензии, ссылка на неё и описание изменений обязательны для рабочего процесса.

Текущая рабочая база содержит записи с готовыми фотографиями. Игрока без проверенного фото можно пока вообще не добавлять: его полное имя остаётся в HTML состава. Модуль также пропускает запись без `image`, но текущий валидатор требует `image` у каждой записи: не добавлять заготовки с `null`, пустым URL или несуществующим файлом ради количества.

## Как состав связывается с базой

Новый состав должен находиться в HTML уже к моменту выполнения общего `menu.js`:

```html
<section class="lineups" aria-labelledby="lineups-title">
  <h2 id="lineups-title">Составы</h2>
  <div class="lineup-grid">
    <article class="lineup-card">
      <h3>Название команды</h3>
      <ol>
        <li data-player-id="will-stuart">Уилл Стюарт</li>
        <li>Финн Расселл</li>
        <li>Игрок без фотографии</li>
      </ol>
    </article>
  </div>
</section>
<script src="/menu.js?v=20260925-photos" defer></script>
```

Это пример структуры, не состав и не номера реального матча. На новой полноценной странице также нужны обычные стили сайта и Матч-центра. Не подключать `menu.js` или модуль карточек второй раз, если он уже есть в шаблоне.

Модуль обходит `.lineups .lineup-card li`:

1. Если есть `data-player-id`, ищет запись именно по нему. Ошибочный ID не подменяется догадкой по тексту: имя остаётся обычным.
2. Иначе сопоставляет **весь текст** элемента с `name` и `aliases` после нормализации: нижний регистр, `ё` → `е`, удаление краевых/повторяющихся пробелов, удаление конечной пометки `— капитан` или `– капитан`.
3. Остальные знаки, дефисы и варианты транслитерации не угадываются. Для нового варианта добавить alias либо явно указать `data-player-id`.
4. Неоднозначный alias двух разных игроков в браузере не распознаётся; валидатор запрещает такие коллизии. Для тёзок использовать разные ID и явное связывание.
5. `li`, уже содержащие ссылку или кнопку, модуль пропускает, чтобы не ломать их поведение.

Номер задаётся обычным `<ol>`/`start`, не частью имени. Полный текст фамилии и капитанская пометка сохраняются при превращении в кнопку. Если хочется показывать сокращённое имя, явно задавать `data-player-id`.

Путь к данным всегда `/assets/players/players.json`, поэтому глубина URL матча не влияет на повторное использование. Все существующие полноценные страницы с этой разметкой и общим `menu.js` используют одну базу. Отдельного списка матчей в базе игроков нет. Обход DOM выполняется один раз: составы, вставленные позже другим JavaScript, автоматически не подхватываются. Сейчас составы статические; эту модель следует сохранять при добавлении следующего матча.

## Порядок работы с новым матчем

1. Получить актуальный репозиторий, прочитать этот документ и текущий `players.json`.
2. Подготовить проверенные составы, сохраняя существующий шаблон и обычный текст имён.
3. Сначала сопоставить игроков с общей базой по полному имени/aliases; проверить тёзок. При необходимости добавить только alias или `data-player-id`. Уже имеющиеся фото повторно не скачивать и не копировать.
4. Для отсутствующих игроков искать разрешённые изображения только в пределах текущей задачи. Недоступный источник или долгий поиск пропустить; публиковать состав можно без этих фото.
5. Успешные новые фотографии добавлять в ту же базу. Игроков прошлых матчей оставлять в ней, даже если сейчас они нигде не показаны.
6. Проверить и опубликовать изменения обычным способом проекта. После публикации убедиться, что новые фото открываются на живом домене.

## Добавление и обновление фотографии

### Новый игрок

1. Проверить, что человека ещё нет под другим написанием имени.
2. Проверить личность на фото и условия повторного использования. Нахождение изображения в поиске, соцсетях или на официальном сайте клуба само по себе не даёт разрешения.
3. Сохранить автора, страницу конкретного файла, год, лицензию и её версию, сведения об исходном кадрировании/редакторе. При необходимости сохранить подтверждение разрешения в служебной документации, не публикуя личную переписку.
4. Скачать с ограничением времени. Практический предел одной попытки — 25 секунд; не запускать бесконечные повторы. Недоступность файла не блокирует других игроков или публикацию матча.
5. Подготовить локальный WebP: максимум 400 px по ширине и 440 px по высоте, с сохранением пропорций; не увеличивать маленький исходник. Ориентир качества — 80–85, размер меньше 100 000 байт (предел валидатора). Проверить резкость лица и ориентацию глазами. Не генерировать и не подменять лицо.
6. Сохранить как `assets/players/<id>.webp`, добавить запись в `players.json`, дополнить сведения об авторстве в `assets/players/README.md`. Новые source-записи можно дописывать в журнал; не стирать прежние результаты.
7. Выполнить проверки ниже. В коммит должны входить и запись, и файл изображения, и сведения о правах.

### Существующий игрок

Без необходимости фото не менять. Если обновление нужно: сохранить `id` и прежние aliases, проверить права на новый снимок, подготовить и осмотреть WebP. Для обновлённого фото предпочтительно новое имя `<id>-<год>-v2.webp` (или следующая версия), чтобы избежать старого браузерного кеша. Обновить в **той же записи** `image.src`, размеры, год, автора, источник, лицензию и описание изменений. Не создавать второго игрока. Старые файлы и сведения об авторстве не удалять вслепую: сначала проверить ссылки; история Git должна сохранять происхождение старой версии.

Существующий валидатор допускает источники по HTTPS и лицензии с домена `creativecommons.org`. Для иного вида подтверждённого разрешения сначала осознанно расширить проверку и формат сведений; не маркировать такое фото произвольной Creative Commons лицензией ради прохождения проверки.

## Поведение и устойчивость

- На ПК наведение мыши запрашивает снимок. Карточка появляется только после успешной загрузки изображения. Уход курсора закрывает её с небольшой задержкой; переход на саму карточку позволяет читать подпись и пользоваться ссылками.
- Нажатие мышью или тап открывает и закрепляет карточку; повторное нажатие, крестик или нажатие вне карточки закрывает её. Поэтому после клика карточка не обязана закрываться от одного ухода курсора.
- Клавиатура: Tab выбирает имя, Enter/Space открывает; ArrowDown переводит фокус внутрь карточки; Escape закрывает и возвращает фокус к имени. Уход фокуса за пределы имени/карточки закрывает её.
- Одновременно используется одна карточка, добавленная в `body`: её не обрезает `overflow` блока состава. Положение ограничено видимой областью, ширина до 260 px; на маленьком экране ограничивается высота, доступна прокрутка. Прокрутка страницы закрывает карточку, изменение размеров пересчитывает положение.
- JSON загружается один раз при запуске модуля. Фотографии **не скачиваются при первоначальной загрузке всех составов**: `Image.src` назначается при взаимодействии с конкретным игроком; результат кешируется в памяти страницы. Внешние источники посетителю загружать не требуется.
- Неизвестное имя/нет фото: обычный текст, без кнопки и пустой карточки. Ошибка получения JSON/модуля оставляет статический состав. Ошибка загрузки изображения возвращает соответствующие кнопки в обычный текст. При медленном ответе карточка остаётся скрытой; отдельного таймера загрузки в браузерном модуле сейчас нет. Переключение/закрытие отменяет показ устаревшего результата.
- Ошибки данных выявлять до публикации через `npm test`; не рассчитывать, что браузер исправит произвольный повреждённый JSON. Никакая фотография не должна быть обязательной для просмотра состава или трансляции.

## Рост и дополнительные поля

Модуль строит общие `Map` по ID и нормализованным именам: один проход по базе, затем поиск для каждого имени состава. Сотни записей не требуют отдельных баз по турнирам; главное — сохранять небольшие изображения и загрузку только по запросу. Сейчас весь JSON загружается целиком. При значительном росте измерить его размер и время обработки до усложнения архитектуры.

Произвольные дополнительные поля записи уже игнорируются карточкой и текущим валидатором. При необходимости можно добавить объект `details` с `position`, `club`, `nationalTeam`, `birthDate` (ISO `YYYY-MM-DD`), `heightCm`, `weightKg`, источниками и датой проверки. Это договорённость для будущего расширения, не существующие заполненные данные: сейчас такие сведения не добавлены и не выводятся. Они не участвуют в идентификации и не должны менять ID. Не заполнять неподтверждённые значения.

## Проверка и публикация

```sh
npm test
npm run build
```

`scripts/check_players.py` проверяет уникальность ID/aliases, локальность и наличие WebP, размер файла, заявленные размеры, обязательные поля авторства и URLs. Это техническая проверка, а не подтверждение лицензии: права и реальное соответствие изображения человеку проверяет редактор. Объявленные размеры также сверять с готовым изображением. Валидатор нормализует регистр, `ё` и пробелы; капитанскую пометку в aliases добавлять не нужно.

После публикации проверить `https://rugby2027.ru/assets/players/players.json`, доступность новых `.webp` и открытие конкретного игрока на `/match-center/`. При изменении самого кода учитывать кеш скриптов; при обычном пополнении отдельные подключения на страницах не нужны. GitHub Pages и браузер могут кратковременно отдавать прежний JSON: это не повод создавать вторую базу или дублировать запись.

Для проверки интерфейса использовать `/checks/player-cards.html`: область шириной 320/375/768/1280 px, оба способа открытия, закрытие снаружи/Escape, отсутствие горизонтальной прокрутки. Это проверка размеров окна в браузере, не проверка на физическом телефоне. Проверить также, что имена без фото остались текстом, а трансляция и партнёрские блоки не затронуты.

Документ и журнал источников находятся в `scripts/`, исключённом из GitHub Pages. Они доступны обслуживающему проект через GitHub и не создают новых индексируемых страниц.
